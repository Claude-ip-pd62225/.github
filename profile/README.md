<h3>为什么先定顺序再定工具</h3>
<p>顺序错了，再好的工具也救不回来。三个号同时登录时，本机出口带宽被三家浏览器争抢，页面加载慢，人一急就去换线路，结果越换越乱。先把顺序定下来，工具按顺序配。</p>
<h3>清单要不要写进制度</h3>
<p>要。写在共享文档里，谁都可以查，交接时不用口头传。三个号以上的团队，口头传一定会漏。</p>
<h2>二、决策一：三条线还是两条线</h2>
<p>理想状态是一号一线。预算不够时，最先被牺牲的应该是使用频率最低的号，而不是把两个常用号塞进同一条线。判断标准看这个号每天要开几次、有没有客户在看。</p>
<h3>必须独占的号</h3>
<p>对外演示的号、绑了支付方式的号、每天在线超过六小时的号，这三类必须独占一条线。它们一旦因为出口共用出问题，损失不是一条线路的钱能补回来的。</p>
<h3>可以临时共用的号</h3>
<p>只做内测、每天开一次、没有绑支付的号，可以两个共用一条线观察，但要记录共用关系。一旦其中任何一个开始出问题，立刻拆开，别等它影响到另一个。</p>
<h2>三、决策二：三个号怎么分地区</h2>
<p>地区分配的核心是「和账号资料对得上」。账号注册地写在哪里，出口就往哪里走。三个号如果注册地不同，硬塞进同一个城市，资料和出口就自相矛盾。</p>
<h3>同城还是分城</h3>
<p>同城的好处是资料一致性好、解释成本低，坏处是三条线在同一城市，某个城市节点整体抖动时三个号一起受影响。折中方案：两个常用号同城，第三个号放隔壁城市作为风险分散。</p>
<h3>城市定了还要对什么</h3>
<p>时区、语言、货币显示三项要跟着城市走。很多人只对了时区，货币还停在默认值，一报价就露馅。这三项在环境包里一次配好，别每次手动改。</p>

<h2>四、决策三：环境用配置目录还是独立设备</h2>
<p>三个号跑在同一台机器上，用不同的浏览器配置目录，成本最低，隔离程度也够用。但主号如果经常要对外演示，建议单独一台设备，减少意外干扰。</p>
<h3>同一台机器的隔离边界</h3>
<p>配置目录分开，Cookie 和本地存储就分开了；但系统级的东西仍然共享，包括字体、时区、代理设置。所以环境里要显式覆盖时区和语言，不能依赖系统默认。</p>
<h3>什么时候值得上独立设备</h3>
<p>三个条件满足两个就该上：每天演示超过一次、账号里有绑定支付、团队里不止一个人操作这个号。独立设备的成本是一次性的，比反复排查串环境要划算。</p>
<h2>五、决策四：早上的登录顺序</h2>
<p>顺序的原则是「重要的先上、慢的后上」。主号先登，等它进入正常会话状态再开第二个。三到五分钟的间隔足够，不需要更久。</p>

<h3>为什么要留十分钟观察</h3>
<p>很多问题不是登录时暴露的，而是三个号同时在线之后才出现。留十分钟专门看这个，比登完就干活要稳。</p>
<h3>登录失败先做什么</h3>
<p>先看环境目录，再看出口 IP，最后才怀疑线路。顺序反了会白折腾半小时。目录对了、出口对了，问题多半在账号本身，直接启用备用号。</p>
<h3>把清单贴到开机台面上</h3>
<p>清单写进文档只是第一步，真正起作用的是把它压缩成一张 A5 纸，贴在开机的位置。人早上脑子还没转起来，看得见的东西才会被执行。</p>
<p>纸上留出「今天换了什么」「哪个号异常」「谁处理的」三行手写空格，一周下来回看，异常规律自己就浮出来了。每月再回看一次那六项决策，业务量、客户地区、账号数量变了就跟着调，命中「什么情况下改」那一列才动。</p>
<h2>常见问答</h2>
<h3>三个号一定要三条线吗？</h3>
<p>答：不一定，但常用号建议独占。判断标准是这个号的使用强度和对外暴露程度，强度低的号可以临时共用，前提是记录清楚共用关系。</p>
<h3>同城三线会不会一起出问题？</h3>
<p>答：同城节点整体抖动时确实会一起受影响。所以常用号同城、备用号另城的组合更稳，既能保证资料一致，又留了一条退路。</p>
<h3>配置目录隔离够不够？</h3>
<p>答：对多数日常使用够用。要注意系统级的时区、语言、字体仍然共享，需要在环境里显式覆盖，否则会出现出口在海外、系统仍是本地时区的矛盾。</p>
<h3>早上登录被要求验证怎么办？</h3>
<p>答：先确认出口城市与资料一致，再确认真实环境没有和别的号共用目录。两项都正常时，按平台提示完成验证即可，不要反复重试。</p>
